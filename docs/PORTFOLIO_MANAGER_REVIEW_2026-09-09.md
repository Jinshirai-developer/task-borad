**優先して直す指摘**

P1はポートフォリオの主要導線として見せる前に直したい点、P2は利用を続ける際の実用性・保守性を高める点です。機能不具合、現行仕様の不足、採用側の評価を区別しています。

1. **P1・表示不具合：標準デモで相談・引き継ぎの表示が切れる**

   再現：登録不要デモを開く → 「サンプル制作チーム」へ切り替える。通常のデスクトップ表示で、「APIの仕様をまとめる」の受け渡し待ち、「ペットの表情をデザイン」の相談中・メモがカード下部で切れ、ラベルを十分に読めません。375px幅でも後者の相談状態が見切れます。大量データや異常に長いタイトルを用意する前の、標準サンプルで発生しました。

   原因はカード・行を152pxに固定し、内容をoverflow:hiddenにしている構造です。担当者・タグ・チェックリストが折り返すと、後ろに追加された重要な状態が押し出されます。

   根拠：frontend/options.css:143–147、frontend/style.css:115–127、frontend/task-details.jsのbadges。

   改善：カードを内容に応じて伸ばすか、相談・引き継ぎ・期限など必須情報の表示領域を確保する。補足情報は省略数つきにまとめる。完了条件は、標準チームデモと複数タグ・長い担当者名で、重要な状態と操作が欠けずに見えることです。

2. **P1・入力保護の不足：Escや背景クリックで未保存の編集を失う**

   再現：個人デモのカードで「編集」 → タイトルを「審査テスト：未保存の入力」に変更 → Esc → 再度「編集」。確認なしで閉じ、入力した文字列は残っていません。ソース上、背景クリックも同じcloseEditModalを呼びます。作成画面も閉じる際にフォームをリセットします。

   根拠：frontend/app.js:300付近、1333–1344、1373–1390。作業メモ側には未保存入力の破棄確認があり、画面間で挙動が異なります。

   改善：編集済みかを検知し、意図しない閉じ方には破棄確認または下書き保持を用意する。保存済みデータが消える不具合ではありませんが、長い説明やチェックリストの入力を失うため、業務画面として大きな減点です。

3. **P1・使いやすさ：スマートフォンの最初の画面にタスクも追加ボタンもない**

   再現：デモを375×812で表示し、先頭から見る。モード説明、ブランド、タグ、ユーザー、ペット、規約リンクが先に積まれ、タスクと「＋」はスクロール後に現れます。

   根拠：実画面、frontend/index.htmlのsidebar→mainという配置、frontend/options.cssの小画面レイアウト。

   改善：小画面ではヘッダーを縮め、ペットの詳細を折りたたむ。最初に現在のワークスペース、追加、タスクを見せる。ペットの存在は残せますが、毎回の操作開始を遅らせない配置が必要です。実機タッチ操作の検証は別途必要です。

4. **P1・提出準備：第三者が試すための公開URLがREADMEにない**

   READMEのアプリ・デモリンクはlocalhost:5097で、公開準備中と明記されています。他のPCの閲覧者はこのリンクから作品を試せません。

   根拠：README.md:8–10。

   改善：まず登録不要デモを第三者が開ける入口として整える。共有や保存を実績として見せるなら、その機能の確認方法も分けて説明する。公開版の起動・主要操作を提出するリビジョンで確認する。今回、公開作業は行っていません。未コミット・未追跡の変更も多く、現在のローカル状態と提出先の状態は別途照合が必要です。

5. **P2・機能不足：必要なタスクを探す基本機能が弱い**

   検索UIはTODO・DOING・DONEそれぞれの虫眼鏡から開き、対象ステータスは変更できません。状態が分からないタスクを横断検索する入口がありません。並び順は作成日時の新旧のみ。担当者、今日の期限、期限超過、期限順で絞る・並べる操作もありません。タイトル検索は説明文を対象にしません。

   根拠：frontend/index.html:282–325、frontend/app.js:1393–1408、TasksController.csのGet、Services/TaskService.cs:41–52、80–94。

   改善：同一ワークスペースの全状態検索、「自分の担当」「期限超過」「今日まで」、期限順を優先する。ペットやテーマをさらに追加するより、実務での利用価値を説明しやすくなります。全ワークスペースを横断する検索まで最初から要求するものではありません。

6. **P2・操作負担：よく使う状態変更がドラッグまたは編集フォームに依存する**

   カード上の主な操作は「編集」「メモ」です。状態変更はドラッグか、「編集」→ステータス選択→保存が必要です。チェックリストも編集画面内にあります。編集フォームには多くの項目があり、表示条件によって保存まで内部スクロールが必要です。

   改善：カードに短い状態選択や完了操作を用意する。詳細な説明・チェックリスト管理は必要時に開く。キーボードやタッチでも、単純な完了操作を少ない手数で実行できることを確認する。

7. **P2・機能不足：相談・SOSに気づく仕組みが弱い**

   メール・プッシュ通知がないことはREADMEに明記されています。現行の自動更新は選択中のチームを15秒間隔で読み、編集中や別ダイアログ表示中は停止します。相談一覧も現在のワークスペース単位で、全所属チームから「自分宛ての未対応」を知らせる入口は見当たりません。

   根拠：README.mdのSOS仕様、frontend/task-details.js:113–155、frontend/companion-work.jsのapiRootとhub。

   改善：チーム機能を主軸にするなら、まずアプリ内で自分宛ての未対応件数を見せ、対象へ直接移動できるようにする。外部通知まで必須とはしません。「SOS」という名称を使う以上、宛先を指定して保存できるだけでは、助けが必要な人の問題を十分に解決していません。

8. **P2・継続利用の不足：変更履歴・長期の復旧・蓄積データの整理が弱い**

   チームタスクは全メンバーが変更・削除できる仕様です。Undoは画面上15秒、サーバー側30秒です。誰がいつ何を変更したかを閲覧する一般的なタスク変更履歴、ごみ箱、アーカイブ、エクスポートは、今回確認した画面・モデル・APIにはありません。ワークスペースのタスク上限は完了済みを含め500件です。

   根拠：README.md、Services/TaskDetailsService.csのSaveUndo、frontend/task-details.jsのofferUndo、Services/TaskService.cs:11とCreateの上限判定。

   改善：すべてを一度に増やす必要はありません。チーム利用を売りにするなら変更履歴・復旧を、個人の長期利用を売りにするならアーカイブを優先する。短時間のUndoは評価できますが、翌日に誤削除に気づく運用を支えられる仕組みではありません。

9. **P2・設計上の制約：全利用者の書き込みを共通ロックで直列化している**

   WorkspaceWriteScopeはstaticのMonitorと固定キーのPostgreSQL advisory lockを使用します。別ユーザー・別チームの更新も同じロックで待ちます。小規模デモの整合性を守る設計として理由は理解できますが、多人数への拡張性を示す実績にはなりません。

   根拠：Services/WorkspaceWriteScope.cs:12–27。READMEにも共通ロックの細分化未実施とあります。

   改善：まず採用理由、想定規模、トランザクション境界、どの競合を防ぐのかを説明できるようにする。規模拡大の必要が生じたらユーザー・ワークスペースごとへの分割などを検討し、独立したチームの更新を並行実行して検証する。今回負荷試験はしていないため、「何人で遅くなる」とは断定しません。

10. **P2・品質保証：テストの成功を画面品質の証明にできていない**

    バックエンド265件、Node120件は今回成功しています。一方、標準デモのカード見切れと未保存入力の喪失を実画面で確認しました。既存NodeテストにはスタブDOMやソース検査も含まれます。CIにはAPI試験・マイグレーション試験がありますが、実ブラウザの主要フローや375px表示を検査するステップはありません。usability-smoke.mjsとcompanion-smoke.mjsも現在のCIからは呼ばれていません。

    根拠：.github/workflows/ci.yml、tests/frontend-options.test.cjs等、今回の試験結果。

    改善：全組み合わせを増やす前に、標準チームデモの重要ラベル可視性、作成・編集・完了・取消、未保存入力の保護、小画面の追加導線を継続検証に含める。「スクリーンショットを取得できた」ことと「必要な情報が見える」ことを分けて判定する。

**見た目と企画への評価**

ライトテーマは色・余白・枠の統一があり、全体が雑に崩れている作品ではありません。ただしタイトル13px、説明11pxのカードに、優先度・期限・タグ・担当者・チェックリスト・相談状態・作成者を詰め込んでいます。画面全体には余白がある一方、判断に使う情報は小さなカード内で混み合っています。「余白があるから見やすい」とは評価できません。

ペットは完了の楽しさを作る差別化要素として残す価値があります。ただし、6テーマ・5レイアウト・6種類のペットの豊富さが、案件で求められる設計判断を直接証明するわけではありません。ここへ追加投資するより、「誰のどの困りごとを減らしたか」を一つの操作シナリオで説明できるようにした方が、営業資料として強くなります。

例：「小規模制作チームが、自分の担当と期限を確認し、困ったタスクに相談を付け、完了を相棒と喜べる」。この説明に対して、担当・期限の絞り込みや相談への気づきが足りない、という順序で改善すると仕様に一貫性が出ます。個人利用を主軸にする選択も可能で、その場合は日々の追加・完了の速さを優先します。

READMEは実装機能と未実施事項を正直に分けている点を評価します。一方、設計上の選択とその理由、短い実演手順、第三者が試せる入口を先頭に置くと、採用側が短時間で判断しやすくなります。DEPLOYMENTの報酬解放に関する古い説明と現行READMEにも差があるため、提出前に現行仕様へ整理する必要があります。

**修正の順番と再審査の条件**

1. カード見切れと未保存入力の保護を修正する。
2. スマートフォンの最初の画面に追加とタスクを見せ、状態変更を短くする。
3. 全状態検索・自分の担当・期限超過・期限順を整える。
4. 標準デモを第三者が開ける形にして、3分以内で主な価値を体験できる手順をREADMEに載せる。
5. 修正した主要フローを実ブラウザと実APIで再確認し、提出リビジョンと一致する検証記録を残す。

上記を満たせば、ポートフォリオとして見せる判断はしやすくなります。MFA、外部ログイン、AI機能、さらに多くのテーマ、大企業向け権限体系まで追加することは、この段階の合格条件にはしません。
